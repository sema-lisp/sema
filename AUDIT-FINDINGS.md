# Audit Findings — Sema simplification audit (2026-08-16)

Full multi-agent audit: 30 subsystems, 44 findings, 5 independent adversarial
critic passes (coverage / duplication / materiality / schema-completeness /
priority). Top-tier findings (high-confidence, low-risk) were implemented
directly — see git log. Everything below is the remainder: deferred, rejected,
lower-priority, and unreviewed-scope items, kept here so they are not silently
lost.

## Rejected or narrowed by the materiality critic — do not implement as proposed

- **eval**: Import/force single-flight gate unification — the two diverged on purpose after a cancellation-safety bug fix (commit 249cf3ef). Only 2 instances exist. Defer until a 3rd gate type appears.
- **workflow-view**: F1 (host/worker MCP resolve unification) was marked DEAD with the claim that `WorkflowMcpResolver::resolve/resolve_prepared` "do not exist anywhere in the repo (confirmed via grep)". That evidence was wrong — both are real trait methods (crates/sema-stdlib/src/workflow_mcp.rs:476 and :493) and `RealResolver` implements both (crates/sema/src/workflow_mcp.rs:116-129). The underlying recommendation is still not a pure refactor: the split exists because ConnectedClient/Value are not Send, and `login_interactive` spins its own tokio runtime that would panic if nested (see the RealResolver comment at crates/sema/src/workflow_mcp.rs:144-156). Treat F1 as deferred-for-design-reasons, not dead, if pursued later. F2 (journal-segment unification across auth.rs/ingest.rs/workflow_evidence.rs) silently changes behavior on the gap-handling case at one call site — that is a semantics decision, not a pure refactor; scope it as one if pursued.
- **policy**: F1 (generic decide<T> over Path/Domain/CommandConstraint) — fail-closed security logic; collapsing 3 auditable checks into one generic trades reviewability for modest LOC savings. Skip. F2 (split ContentAction into two narrower enums) — self-rated low confidence, speculative type-safety with no observed bug. Skip.
- **stdlib-io-system**: CheckoutRegistry<K,T> unification across proc/pty/serial/kv/sqlite — legitimate 5x duplication, but real per-resource teardown differences (SIGKILL process groups vs plain drop/close). If pursued, do incrementally (proc+pty first, the closest twins), never as one sweep. **Status (2026-08-17): the recommended incremental slice was done.** The two `checkout_runtime` fns (proc.rs:353, pty.rs:309) were byte-identical `checkout_external(CheckoutOp{..})` literals differing only in the completion kind and the thread-local registry paths; both now call a shared `crate::runtime_offload::checkout_runtime_op` builder. All teardown (SIGKILL abort hooks, close paths) and error text stay in each module. serial/kv/sqlite/stream remain as-is. Verified by sema-stdlib + the full async suite (162 tests incl. subprocess group-kill cancel).
- **stdlib-collections**: Map-vs-HashMap output-type dedup across ~15 functions — the write-side (merge/assoc-in/deep-merge) decides output type from args[0]s variant, not from any structural property a shared helper could infer, so the write-side win is mostly illusory. If pursued, scope to the read-side only (get/keys/vals/contains?/entries/select-keys/except/get-in).
- **workspace-tooling**: Parameterizing check-unified-runtime-legacy.sh's 4 bash+awk zero-tolerance allowlist gates into one generic checker — real risk of quoting/word-splitting bugs in bash that are harder to spot than the explicit copies, for a security gate. Skip, or narrow to sharing only the byte-identical awk comparator.

## Deferred lower-priority findings (accepted by materiality/schema critics, not yet implemented)

### reader — sema-reader: lexer/parser
Ownership: crates/sema-reader/src/*.rs
- **Collapse repeated single-char delimiter token arms in the lexer into a table lookup** (confidence: high)
  - **Status (2026-08-17): implemented.** Added `single_char_token(char) -> Option<Token>` and a single guarded match arm for the 9 delimiters; `,` and all other special cases unchanged. All 203 sema-reader tests pass.
  - Evidence: crates/sema-reader/src/lexer.rs:112-226 — 9 near-identical match arms ('(', ')', '[', ']', '{', '}', quote, backtick, '@') each executing the exact same 5 statements: `col += 1; i += 1; tokens.push(SpannedToken { token: Token::X, span: span.with_end(line, col), byte_start: byte_offsets[i - 1], byte_end: byte_offsets[i] });` — only the `Token::X` variant differs.
  - Proposed: A `const SINGLE_CHAR_TOKENS: &[(char, Token)]` (or `fn single_char_token(ch: char) -> Option<Token>`) covering `( ) [ ] { } ' ` @`, plus one shared block that does the `col`/`i` advance, span, and `SpannedToken` push once, checked before falling into the existing `,` (two-char lookahead), `"`, `#`, `:`, and numeric/symbol special cases which stay as-is. `Token` is already `Clone`, so returning an owned clone from the table is trivial.
  - Scope: crates/sema-reader/src/lexer.rs only, inside `tokenize()`. No public API change — `Token`, `SpannedToken`, and `tokenize`'s signature/behavior are unchanged; purely an internal restructuring of the match.
  - Risks: Very low: these are unconditional single-character, no-lookahead tokens with identical bookkeeping — a scan-order bug would show up immediately as wrong spans/token types in existing tests. Byte offsets must stay indexed as `byte_offsets[i-1]`/`byte_offsets[i]` after the same `i`/`col` increments, which is easier to get right once instead of nine times.
  - Validation: Existing lexer unit tests in crates/sema-reader/src/lexer.rs (test_comment_token_emitted, test_newline_token_emitted, test_trivia_order_preserved, etc.) plus the much larger reader.rs parser test suite (which round-trips every bracket/quote form) already exercise all 9 tokens; run `cargo nextest run -p sema-reader` to confirm.
- **Deduplicate the mismatched-closing-bracket checks in parse_list/parse_vector/parse_map** (confidence: medium)
  - **Status (2026-08-17): implemented.** Added `check_no_foreign_closer` and routed all six blocks (per-opener hint, exact message wording) through it. All 203 sema-reader tests pass, including the six mismatch tests + recovery test.
  - Evidence: crates/sema-reader/src/reader.rs — parse_list (222-235), parse_vector (265-278), and parse_map (301-314) each repeat the same shape twice (once per other closer), e.g. `if self.peek() == Some(&Token::RBracket) { return Err(SemaError::Reader { message: "mismatched bracket: expected `)` to close `(`, found `]`".to_string(), span: self.span() }.with_hint(...)); }` — 6 near-identical blocks total, differing only in which two of `)`/`]`/`}` are 'foreign' to the current opener.
  - Proposed: A small shared helper, e.g. `fn check_no_foreign_closer(&self, open_char: &str, close_char: &str, foreign: &[Token]) -> Result<(), SemaError>` that peeks at the current token and, if it matches one of the 'foreign' closer tokens, builds the 'mismatched bracket: expected `{close_char}` to close `{open_char}`, found `{token_display(...)}`' message generically. Called once at the top of each of the three loop bodies (passing the other two closers) instead of two inline `if` blocks each.
  - Scope: crates/sema-reader/src/reader.rs, inside Parser::parse_list, parse_vector, parse_map only. No change to SemaError, Token, or any public read* function signature — purely internal.
  - Risks: Low: message wording must stay recognizable ('mismatched...') and the per-opener hint text must still match; six dedicated tests already pin this. A careless generic rewrite could accidentally swap which two closers count as 'foreign' for a given opener, silently allowing an invalid combination through.
  - Validation: The 6 existing tests test_mismatched_paren_bracket, test_mismatched_bracket_paren, test_mismatched_paren_brace, test_mismatched_brace_paren, test_mismatched_brace_bracket, test_mismatched_bracket_brace (reader.rs ~2041-2096) plus recover_mismatched_bracket (~2181) directly cover this refactor's surface; run `cargo nextest run -p sema-reader`.

### stdlib-misc — sema-stdlib: math/datetime/diff/git/reflect/meta/otel
Ownership: crates/sema-stdlib/src/arithmetic.rs, bitwise.rs, math.rs, datetime.rs, diff.rs, git.rs, memory.rs, meta.rs, reflect.rs, otel.rs, archive.rs, context.rs, regex_ops.rs
- **`+`, `-`, `*` each hand-roll the same i64→f64→bignum accumulator state machine** (confidence: high)
  - **Status (2026-08-17): implemented.** Added `fold_through_tower(values, identity, seed, fold)` with `ADD/SUB/MUL` folds; `+`/`*` use seed==fold, `-` seeds with `ADD` then folds `SUB` (reproduces the first-element pass-through including the i==0 float overwrite), and the unary-negation case stays a special case. `sum_through_tower` is now a thin wrapper so `list/sum` is untouched. Verified by manual edge-case smoke (overflow/underflow/bignum/float contagion/left-fold/unary) and the full sema-lang eval suites (4915 green).
  - Evidence: crates/sema-stdlib/src/arithmetic.rs:17-73 defines `sum_through_tower` (used by `+` at line 107 and by `list/sum` in list.rs:2967-2973) as the single shared implementation of the three-tier accumulator: an i64 fast lane, promotion to f64 once any float operand is seen (`has_float`), and promotion to an arbitrary-precision `SemaNumber` tower once an i64 op overflows or a bignum operand appears (`tower: Option<SemaNumber>`). The doc comment on `sum_through_tower` explains it was extracted specifically because `list/sum` once reimplemented this by hand and diverged ("a bare `int_sum += n`, which wrapped silently past i64::MAX" and rejected bignums with a self-contradictory error). Despite that lesson, `-` (arithmetic.rs:109-194) and `*` (arithmetic.rs:196-254) still each hand-roll their own copy of the identical `has_float`/`int_acc`/`float_acc`/`tower: Option<SemaNumber>` state machine inline in `register()`, ~85 and ~60 lines respectively, differing from `sum_through_tower` (and each other) only in which `SemaNumber`/i64/f64 operator is applied and, for `-`, that the first element seeds the accumulator directly instead of via `identity op first`.
  - Proposed: Factor a single generic `fold_through_tower(args, identity: i64, seed_op: TowerOp, fold_op: TowerOp)` (where `TowerOp` is a small struct/tuple of `fn(i64,i64)->Option<i64>`, `fn(f64,f64)->f64`, `fn(SemaNumber,SemaNumber)->SemaNumber`) that owns the has_float/int/float/tower promotion logic exactly once. `+` and `*` call it with `seed_op == fold_op` (Add/identity 0, Mul/identity 1); `-` calls it with `seed_op = Add` (so index 0 passes the first operand through unchanged, matching `0 op first == first`) and `fold_op = Sub`. `sum_through_tower` becomes a thin wrapper (or is replaced outright, keeping its name/signature for `list/sum`'s call site). The existing `-`-with-one-argument negation special case stays as its own early return (it is not a fold at all).
  - Scope: Single file: crates/sema-stdlib/src/arithmetic.rs. No public API changes — `sum_through_tower` keeps its `pub(crate)` signature so crates/sema-stdlib/src/list.rs:2967-2973 (`list/sum`) is untouched. `+`, `-`, `*`, `/`, `mod`/`modulo` builtin names and behavior are unchanged.
  - Risks: Must preserve every existing edge case exactly: i64 overflow promotion, mixed int/float contagion (including which operand order triggers the float conversion), bignum operands, and the unary `-` negation path (which is NOT foldable the same way and must stay special-cased). A subtle risk is that `-`'s float short-circuit currently *overwrites* `result_float` at i==0 rather than adding to it — the proposed seed_op=Add reproduces this only because identity is 0; must verify with the boundary tests below rather than assume.
  - Validation: Existing coverage in crates/sema/tests/suites/eval_test.rs already exercises exactly this logic end to end: `big_int_add_overflows_small`/`big_int_sub_overflows_small` (line 16/18), `add_overflow_promotes`/`sub_underflow_promotes`/`mul_overflow_promotes` (1433-1435), `bignum_*_overflow_promotes` (1454-1456), `vm_add_overflow_promotes`/`vm_mul_overflow_promotes` (1471-1473), `boundary_add_max_direct`/`boundary_sub_min_direct`/`boundary_mul_overflow_direct`/`boundary_neg_min`/`boundary_add_inexact_direct`/`boundary_round_trip_to_fixnum` (1811-1838), plus rational/complex cases (1507-1508, 1546). Run `cargo nextest run -p sema-lang --test eval_suite` (or the relevant suite binary) before and after; add one new case asserting `+`/`-`/`*`'s promotion behavior stays identical if the refactor introduces a shared helper, mirroring the existing `list/sum`-vs-`+` regression test pattern.
